# Web

The web app in `web/`: its stack, the rules that keep it portable between Vercel and a container, its image, Google sign-in, studying decks, the legal documents, its theme and the user's choice of it, and its checks.

## Current decisions

### Project

- `web/` is a Next.js 16.4.1 App Router project of its own, with strict TypeScript and the `src/` layout of stack-nextjs.md §1 ([ADR 0019](adr/0019-web-app-stack-portability-and-sign-in.md)). It runs on Node.js 24.22.0, named once in `web/.nvmrc`.
- Its packages are pinned exactly in `web/package.json` and locked in `web/package-lock.json`. Dependabot's `npm` entry for `/web` proposes their moves, except TypeScript 6.1 and later, ESLint 10 and later, and `@types/node` 25 and later:
  - typescript-eslint 8.71.2 accepts TypeScript below 6.1;
  - eslint-config-next 16.4.1 brings React, import and jsx-a11y lint plugins that accept ESLint 9 at most;
  - `@types/node` follows `web/.nvmrc`, which the PM moves with the Dockerfile's base image.
- Its features live under `web/src/features/` ([`structure.md`](structure.md)): `auth`, `decks` and `study`.
- Every user-facing string is Korean, in 해요체, written where it is rendered; the root layout declares `lang="ko"`.
- Icons are `lucide-react`'s, pinned exactly like every package ([ADR 0027](adr/0027-draw-both-clients-in-the-smartman-brand-and-the-v2-screens.md)).

### Portability

- No Vercel-only feature: no `@vercel/` package and no `runtime = 'edge'` anywhere under `web/`. `make lint` fails on either through `web.sh`, after checking that its pattern still finds both in two control lines.
- The build is `output: "standalone"`, and runs on the Node.js runtime.
- On Vercel the functions run in `hnd1` (Tokyo, AWS `ap-northeast-1`), the Supabase project's region, so each request a page makes to Supabase stays within one region ([ADR 0030](adr/0030-read-only-what-each-web-page-shows-and-size-the-web-from-the-app-tokens.md)). `web/vercel.json` declares it, as `regions`, and holds nothing else: a container never reads the file, and a key that changed behaviour, a rewrite or a header, would make Vercel and the container differ. Vercel reads the file from the project's Root Directory, `web`, and it overrides the region set in the project's settings. Vercel's function-region documentation (updated 2026-08-11) deploys Routing Middleware to every region whatever this setting says; `proxy.ts` makes no request to Supabase while the signing key is cached in the process and the session's access token is fresh, so where it runs adds no request to a page. A container runs where it is deployed, and its operator places it near the Supabase project.
- The configuration is environment variables, parsed once by `web/src/env.ts`: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. A missing or malformed value, or a key that is not a publishable key, fails the build. All are public, and no secret is read: the app uses the publishable key and the user's session.
- They are frozen into the build, so a build, and an image, belongs to one Supabase project. `web.sh` builds with the values of `app/config/dev.json` unless the environment already sets them.
- `GET /api/health` answers `{"status":"ok"}` with 200 and reads nothing.

### Image

- `web/Dockerfile` is built from the repository root: `docker build -f web/Dockerfile .`, with both variables as `--build-arg`. `web/Dockerfile.dockerignore` admits only `web/`, `app/assets/fonts/` and `engine-wasm/pkg/` ([ADR 0022](adr/0022-study-on-the-web-with-the-engine-in-the-browser.md)).
- Three stages install the locked packages, build, and copy the standalone server, the static files and `public/` into the runtime stage. Each starts from the same index digest of `node:24.22.0-trixie-slim`, and the frontend is pinned by digest in the `# syntax=` line.
- The runtime stage runs `node server.js` on port 3000 as the base image's `node` user, uid 1000.
- Dependabot's `docker` entry for `/web` proposes only a new digest of the same `node:24.22.0-trixie-slim` tag; it ignores every Node.js release change. `make lint` fails while a `FROM` names another release than `web/.nvmrc`, and `web.sh` fails while the running Node.js differs from that file, so a release change moves `web/.nvmrc`, the `node-version` of `.github/workflows/ci.yml`'s `setup-node` step and the three `FROM` digests together, which Dependabot cannot do. The PM moves them, in one PR, to a new LTS release verified per ci.md.
- What the image runs is the web app alone; nothing in it may reach a Supabase secret.

### Sign-in

- The session is Supabase Auth's, in the cookies `@supabase/ssr` writes. `web/src/lib/supabase/` holds the server client, over the request's cookies, the browser client, and `readSession`, which verifies a session with `getClaims` and returns `signed-in` with the email, `signed-out`, or `unreachable`.
- The server client waits for the request (`connection()`) before it starts: Supabase Auth's client reads the clock as it starts, which a prerender, a link's prefetch included, refuses.
- `web/src/proxy.ts` runs on every path but `/api`, `_next/static`, `_next/image`, `favicon.ico`, `brand/` and the `.svg`, `.png` and `.webmanifest` files of `public/`. It refreshes the session cookies and sends a `signed-out` visitor to `/login` from every path but `/login`, `/auth/callback`, `/terms` and `/privacy`. An `unreachable` Supabase lets the request through, so an outage signs no one out.
- `/login` follows the phone's sign-in screen and the SignIn artboard: the stacked lockup, 200 wide, as the heading and the phone's welcome sentence on the ground's panel, rounded at the foot, then on the surface Google's button, "Google로 로그인", and the consent line with the legal links. The button calls the browser client's `signInWithOAuth` for Google, with `redirectTo` the page's origin plus `/auth/callback`; while it starts, progress takes the mark's place and the button cannot be pressed again, and a failure to start is shown beneath it.
- The button is Google's, drawn to its branding guidelines (developers.google.com/identity/branding-guidelines, last updated 2026-07-07, re-read 2026-10-16) as the phone draws it ([ADR 0024](adr/0024-one-voice-and-a-sheet-action-rule.md), [ADR 0031](adr/0031-keep-the-web-theme-choice-in-the-browser-draw-google-sign-in-at-the-app-height-and-hold-each-page-with-a-skeleton.md)): the light button in the light theme and the dark one in the dark, with `GoogleButtonStyle`'s fill, 1 px stroke and label colours and its 14/20 medium label as `@theme` tokens (`google-*`), the guidelines' Android and web spacing, 12 px, 10 px and 12 px, and 56 high with the 16 px radius, the app's, since the guidelines name no height. Its "G" mark is `web/public/google/g-mark-light.png` and `g-mark-dark.png`, byte for byte the app's `app/assets/google/4.0x/` PNGs from Google's bundle ([`design.md`](design.md)), drawn at 20 px.
- `/auth/callback` is a Route Handler. It exchanges the code for the session cookie and opens `/`, or opens `/login?error=cancelled` when no code arrives and `/login?error=failed` when the exchange fails; `/login` shows the matching sentence.
- `/account` reads the session on the server and shows the account's initial and email and "로그아웃", or that the server cannot be reached; the home page's avatar opens it.
- Sign-out is the Server Action `signOut`, through the `auth` feature's `actions.ts`; while it runs, the row shows progress in place of its icon and cannot be pressed again. It revokes this browser's session alone (`scope: "local"`), so the phone stays signed in, and opens `/login`. When Supabase cannot be reached it returns the sentence the form shows.
- Each origin the app is served from must be in Supabase Auth's allowed redirect URLs as `<origin>/auth/callback`. Only the owner changes that list.

### Decks and study

- The web app is online-first: it reads and writes the server tables of [`server.md`](server.md) with the user's session, under row-level security, and keeps no local database. Nothing creates or edits decks or cards on the web.
- Reads run on the server, in each page's Server Component, and read only what the page shows, with no cache ([ADR 0030](adr/0030-read-only-what-each-web-page-shows-and-size-the-web-from-the-app-tokens.md)):
  - `/` reads `decks`' `readDeckList` (every deck, and each card's id, deck and creation time, without its sides), `study`'s `readCardStates`, `study`'s `readPace` (the duration of the latest 200 reviews) and `study`'s `readToday`, together;
  - `/decks/[id]` and `/study` read `readLibrary` over the decks they name (those decks and their cards with both sides), `readCardStates` and `readToday`, together; `/study` asks `readToday` for the streak too.
- `readToday` reads today's study day ([ADR 0033](adr/0033-count-cards-left-per-study-day-from-04-00-and-continue-as-unrecorded-practice.md)): every answer since the day began, then, for the cards answered today, whether each was answered before, in requests of 100 card ids each, sent together, to count the new cards first answered today; and, for the streak, the answers before today, newest first, a page at a time until a day without one decides it. It reads the day in the time zone the cookie `smartman-tz` names, which the root layout's head script writes on every page from the browser's `Intl` zone, the sign-in page included, so it is set before any page that counts; without the cookie, or with a zone the server does not know, it reads the day in Asia/Seoul (`web/src/lib/time-zone.ts`).
- Each read keeps the signed-in user's own rows, since row-level security also lets every user read other users' public decks and their cards ([`server.md`](server.md)), leaves out every row with `deleted_at` set and every card of such a deck, and parses each row at the boundary. It reads its tables in pages of 1000 rows, PostgREST's `max_rows` in `supabase/config.toml`: the first page with PostgREST's exact count, then every remaining page together, so it waits on two requests at most. A failure reaches the page as a value, `unreachable`, `rejected`, `failed` or `unreadable`, which it shows as one sentence in place of the list; the codes map as the phone's do ([`sync.md`](sync.md)).
- The screens follow the principles, tokens and v2 look of [`design.md`](design.md) at desktop width, lists in a centred 560 px column and the study card up to 720 px wide ([ADR 0027](adr/0027-draw-both-clients-in-the-smartman-brand-and-the-v2-screens.md)):
  - `/`: the horizontal lockup as the heading and the account's avatar at the right, then the navy today card, "오늘 할 카드", the count large with "장", "복습 x · 새 카드 y · 약 n분", in a backlog "밀린 복습을 마칠 때까지 새 카드는 쉬어요.", and a white "모두 학습", or with nothing to study "오늘 할 카드를 다 했어요" and no button, then "내 덱 n" and a row per deck, by name: its initial on a tile in the tint the app gives it, "카드 n장", an outlined "공개" chip when the deck is published, a brand-tint "오늘 n" chip when n > 0, a chevron, and a link to the deck named by its name, count and chips. The page carries no account content beyond the avatar;
  - the minutes are the session's cards times the median time of the user's latest 200 reviews, or 10 s a card with fewer than 20, rounded up, as on the phone;
  - `/decks/[id]`: a back link, the name with "공개" beside it when the deck is published, the pills "카드 n", "복습 x" and "새 카드 y", in a backlog the same sentence, "학습하기 · n장", disabled at 0, and the cards, oldest first, as one rounded group of front and back rows, with a search that keeps the cards whose front or back holds it, ignoring case. A deck that does not exist, or is deleted, is not found;
  - `/study?decks=…`: a session over the comma-separated decks, leaving out those that do not exist;
  - the home page of a user with no deck shows, in place of the today card and the list, the phone's first run: the mascot in its 128 px surface circle, "첫 덱을 만들어 볼까요?" and "덱은 휴대폰 앱에서 만들어요. 단어장 사진을 찍거나 직접 입력하면 여기에도 보여요.". It offers no action: the web creates nothing, and has no public-deck browsing to offer "공개 덱 둘러보기";
  - `/account`: the profile card, "화면" with the theme choice, "계정" with "로그아웃", and the mascot and the legal links at its foot;
  - `/terms` and `/privacy`: the documents (below).
- While a page waits on the server, a skeleton of its own layout holds its place ([ADR 0031](adr/0031-keep-the-web-theme-choice-in-the-browser-draw-google-sign-in-at-the-app-height-and-hold-each-page-with-a-skeleton.md)): the today card and three deck rows on `/`; the back link's place, the name, the pills, the study button, the search and four card rows on `/decks/[id]`; the header with its progress bar, the card and the three answer buttons on `/study`; the profile card, the theme choice and the sign-out row on `/account`. Each placeholder is the size of what replaces it, its text lines as tall as their type style's line height, so nothing moves when the content arrives. `web/src/components/skeleton.tsx` draws them: hidden from screen readers, which hear its sentence ("덱을 불러오는 중이에요.", "카드를 불러오는 중이에요.", "계정을 불러오는 중이에요.") in a visually hidden status inside an `aria-busy` region, and pulsing to 40% opacity and back over 1.2 s, as the phone's skeleton rows fade, only under `prefers-reduced-motion: no-preference`.
- `web/src/features/study/queue.ts` holds the queue rules of [`study.md`](study.md), in one module: the study day from 04:00 to 04:00 in a time zone, with 20 new cards less those first answered in it across every deck, never below zero and not carried over; a card due when it falls due before the day ends; a backlog above three days of reviews due, its due cards earliest due first in shuffled runs of ten and no new card; otherwise the due cards and as many new ones as the day has left, oldest first, shuffled; a "모른다" shown again after 3 to 5 other cards; the streak; and the counts the deck screens show, from the same selection ([ADR 0025](adr/0025-order-a-review-backlog-by-due-date-and-pause-new-cards.md), [ADR 0033](adr/0033-count-cards-left-per-study-day-from-04-00-and-continue-as-unrecorded-practice.md)). The study page selects the queue on the server, in the day `readToday` read, and the browser orders it from a random source seeded with that time, so the server's render and the browser's agree. Every random choice of a session, its order, each re-show gap and each answer's fuzz factor, comes from that one source.
- The study screen ports the phone's session ([`study.md`](study.md)) in its v2 look: the split card, question left at 30/800 and answer right at 20/600, centred in each half, hidden until shown, divided by an inset line; the 8 px ink progress bar of cards answered out of the queue, with "n/m"; every answer of the session above the card, newest nearest, each a button that toggles it between "안다" and "모른다" with the phone's queue effects; and, once no card is left, the completion card in the current card's place under the stack, as on the phone: the mascot, "오늘 학습 완료", today's "n 안다", "n 모른다", minutes and streak over the decks, "계속 학습", which takes the focus, and "그만하기", a link to `/`. "계속 학습" goes on as practice on the same page, as the phone's does, writing nothing; with nothing left and nothing answered today the page says "오늘은 학습할 카드가 없어요", with no progress bar. The close button is a link to `/` named "끝내기". Swipe is not offered.
- Keyboard: Space shows the answer, → or K is "안다", ← or J is "모른다", Z toggles the last answer, Esc follows "끝내기" to `/`, and ? lists these in a dialog. Letters are read by their physical key, so they work in any input language. Each has a visible button carrying it in `aria-keyshortcuts`.
- The engine runs in the browser ([ADR 0022](adr/0022-study-on-the-web-with-the-engine-in-the-browser.md)). `web/src/features/study/engine-wasm` links to `engine-wasm/pkg/`, which `next.config.ts` admits in `turbopackAdditionalRoots`; the generated glue fetches its `.wasm`, which the build serves as a static file. The screen starts fetching it when it opens.
- Writes never hold the screen: an answer or a toggle changes it at once, and its write joins a queue that sends one write at a time, in order. A write replays the card's answers of this session, with their fuzz factors, from its state when the session opened, as the phone does, and the Server Action `recordAnswer` stores the result with the session it verifies ([`sync.md`](sync.md)).
- A write that fails stops the queue: it and every write behind it wait, so a toggle never reaches the server before its answer. The screen says what failed in one sentence with "다시 시도", which sends them again; the answers stay in the stack. While a write waits, leaving the page asks first.

### Legal documents

- The web publishes the terms of service at `/terms` and the privacy policy at `/privacy`, in Korean, and every link to them, the app's included, leads there ([ADR 0032](adr/0032-publish-the-legal-documents-on-the-web-and-link-both-clients-to-them.md)). The login page's consent line and the account page's foot link to them by those relative paths, through `web/src/components/legal-links.tsx`; nothing configures them.
- Each page is a static Server Component that reads nothing, so `next build` prerenders it; the proxy lets a signed-out visitor reach both.
- `web/src/components/legal-document.tsx` draws both in the list column with the theme's tokens: the title with a back link, "시행일" and the date, the opening paragraph, a "목차" navigation linking to each section, then each section under a second-level heading whose `id` is its anchor.
- The privacy policy's sections are the items collected and how, the purposes, retention and destruction, third-party provision, processors, overseas transfer, the user's rights, automatically collected data and cookies, protection measures, the contact and the effective date with how changes are announced. The terms' are the service, accounts and sign-in, the user's content and the licence for public decks, public sharing with reports, blocks and prohibited content, AI-made cards, service changes, account deletion, liability, governing law, the contact and the effective date (issue #86).
- Both name the operator as "smartman 운영자" and the contact `sauce@garam.sh`, and take effect on 2026-10-16. A change to either is a pull request to its `page.tsx`, and states the new date.

### Theme

- `web/src/styles/globals.css` declares the colour tokens of `app/lib/shared/theme.dart` ([`design.md`](design.md)) in `@theme`, under the same names in kebab case, the radii of `AppRadius`, the type scale of `AppType` with each style's size, line height, weight and tracking, the 560 px list and 720 px study columns, the card and raised shadows, and Google's button tokens. It overrides each colour with the dark set under `prefers-color-scheme: dark` while the user's choice is not 라이트, and under the choice 다크 whatever the system's mode.
- The user picks 시스템 (the default), 라이트 or 다크 in `/account`'s "화면", a radio group of three native radios labelled by that heading ([ADR 0031](adr/0031-keep-the-web-theme-choice-in-the-browser-draw-google-sign-in-at-the-app-height-and-hold-each-page-with-a-skeleton.md)). The choice applies at once, as `data-theme` on `<html>` (absent for 시스템), and is then kept in this browser's `localStorage` under `smartman.theme`; when the browser refuses to keep it, the page stays in it and says so. The root layout's `<head>` runs an inline script first, before the body is parsed, that sets `data-theme` from the stored choice, so every page's first paint is drawn in it; storage that cannot be read leaves the system's. Tailwind's `dark:` variant follows the same rules as the colours. `web/src/lib/theme.ts` holds the key, the script and the store.
- Spacing and sizes come from the same file ([ADR 0030](adr/0030-read-only-what-each-web-page-shows-and-size-the-web-from-the-app-tokens.md)): Tailwind's spacing unit is pinned at 4 px, so each step of `AppSpace` is a whole number of it; `AppSpace`'s gutter, row gap and section gap are the tokens `gutter`, `row-gap` and `section-gap`; and each `AppSize` value a web screen draws is a token under its name in kebab case (`button`, `cta`, `tap-target`, `deck-tile` …). The markup uses these tokens, not the steps they equal.
- `web/src/styles/__tests__/theme-tokens.test.ts` fails when a colour token differs from theme.dart's, in the light set or in either rule's dark set, a Google button token from `GoogleButtonStyle`'s colours, label, mark size or Android and web spacing, a radius from `AppRadius`, a type style from `AppType` in size, line height, weight or tracking, a size token from the `AppSize` value of its name, a named gap from `AppSpace`'s, or a step of `AppSpace` from a whole number of the spacing unit.
- `web/src/styles/fonts` links to `app/assets/fonts/`. `next.config.ts` names that directory in `turbopackAdditionalRoots`, and the root layout bundles Pretendard's Regular, Medium, SemiBold, Bold and ExtraBold with `next/font/local`; nothing is downloaded at run time.
- `web/public/` holds `favicon.svg`, which follows the colour scheme, `favicon-32.png`, `apple-touch-icon.png`, `icon-192.png`, `icon-512.png` and `manifest.webmanifest` with theme colour `#1F2A44`; the root layout names them, `brand/` holds the marks, and `google/` Google's "G" mark.
- Buttons are at least 52 px high (`min-h-button`), the primary 56 (`min-h-cta`), and the focus ring is a visible outline.

### Checks

- `web.sh`, at the repository root, implements the `web/` part of `make lint`, `format`, `test` and `build`. Where `node` is missing it prints that it skipped; where the host's Node.js differs from `web/.nvmrc` it fails. It installs the locked packages when they are missing or older than the lock file.
- `make lint`: ESLint with typescript-eslint's type-checked strict rules, `tsc --noEmit`, the portability check and the Node.js release check.
- `make format`: Prettier, over the files git tracks or would track.
- `make test`: the Vitest suite (`web/src/**/__tests__/`), then, where Docker and buildx answer, the image built and run, its health and non-root uid asserted, and the Playwright specs in `web/e2e/` run against it; `web/e2e/study.spec.ts` skips there. Then `supabase/test-web.sh` runs that spec against a throwaway local stack (below).
- `make build`: `next build`, then the image where Docker and buildx answer.
- CI runs `web.sh` on the Node.js that `.github/workflows/ci.yml` installs for the WebAssembly tests, on both jobs; `web.sh` fails there when it differs from `web/.nvmrc`. Only the ubuntu job has Docker, so it alone runs the image and the e2e specs, `supabase/test-web.sh`'s included.
